# ScamBrake intervention backend contract

## Public API for Denise

```python
from intervention import build_interventions, build_strategy, build_intervention

cards = build_interventions(analysis)           # All four cards, exact schema below
diversion = build_strategy("diversion", analysis)  # One card, without a wrapper
legacy = build_intervention(analysis)          # Existing Pause & Verify shape
```

Pass the original seven-field `analyzer.analyze_input(confirmed_text)` result.
These calls are deterministic, synchronous, local, and do not mutate the input.
There are no third-party dependencies, network calls, environment reads, file
writes, logging, or provider imports in the engine. OCR and AI analysis remain
the caller's responsibility; do not call the analyzer again just to build cards.

## Input

```json
{
  "scenario": "family_emergency",
  "risk_level": "high",
  "signals": [{"type": "urgency", "evidence": "right away"}],
  "requested_amount": "$2,500",
  "payment_method": "Apple gift cards",
  "claimed_sender": "grandson Jake",
  "explanation": "A fictional request warrants independent verification."
}
```

Supported scenarios, matching the analyzer: `family_emergency`,
`bank_impersonation`, `invoice_fraud`, `suspicious_payment`, `general`, `unknown`.
Supported risks: `low`, `medium`, `high`, `uncertain`. No phishing scenario enum
was added. Phishing/link signals can select an internal link-verification route.

Non-dictionaries normalize to an empty analysis. Unknown/malformed enums become
`unknown` / `uncertain`. Unexpected keys are ignored. Missing/null/invalid details
become `None`. Strings are retained verbatim or dropped, never truncated into a
different quote. Signal types must be 1-64 ASCII characters, start with a letter,
and contain only letters, digits, spaces, underscores, or hyphens. Both type and
nonblank evidence are required. Evidence is limited to 1,000 characters; each
detail to 300; explanation to 6,000. Only the first 32 signal entries are examined.
Control characters other than tab/newline/carriage return are rejected. Cycles in
unexpected data do not cause recursive traversal.

## Exact output

No additional top-level or strategy keys are returned:

```text
{
  "scenario": string,
  "risk_level": string,
  "interventions": {
    "questioning": {
      "title": string,
      "message": string,
      "options": [{"id": string, "label": string}]
    },
    "authority": {
      "title": string,
      "message": string,
      "source": {"name": string|null, "label": string|null, "url": string|null}
    },
    "social_influence": {
      "title": string,
      "message": string,
      "matched_signals": [string]
    },
    "diversion": {
      "title": string,
      "message": string,
      "actions": [{"id": string, "label": string}]
    }
  }
}
```

Question IDs always appear as `yes`, `no`, `unsure`, in that order. Action IDs are
stable semantic identifiers, unique within a card; labels need not be parsed.
Titles are at most 100 characters, messages 3,000, action labels 500, and IDs 64.
There are at most 8 actions and 32 matched signal types. Source metadata must match
a curated source exactly or consist of three nulls. All output is JSON serializable.
`interventions.contract.validate_bundle(result)` checks the agreed shape and bounds.

See [the actual generated examples](intervention_examples.json) for complete valid
input/output structures for family emergency, bank impersonation, invoice fraud,
and an ambiguous low-risk request. These are generated by the executable example
script and checked for contract validity and snapshot parity in tests.

## Strategies and selection

- **Questioning** asks about an independent verification step. It does not infer
  that the user already paid, clicked, or verified anything.
- **Authority** provides relevant general guidance from a specific official page.
  Each message explicitly distinguishes advice from institutional assessment of
  the submitted message. Missing curated sources use null source fields.
- **Social influence** describes documented patterns, not testimonials, prevalence
  numbers, or claims about other ScamBrake users. A scenario can support a family,
  bank, or invoice pattern; individual tactics require actual supported signals or
  a gift-card payment method. A suspicious-payment label alone does not establish
  a particular tactic.
- **Diversion** offers actions through saved contacts, official apps, bank-card
  numbers, or established supplier contacts. It never includes a user-supplied
  phone number, URL, name, amount, or account detail in an action.

Only `medium` and `high` activate scenario-specific pattern guidance. `low`,
`uncertain`, invalid risk, and incomplete analysis receive general questioning,
general actions, and neutral social text. The top-level valid scenario is still
preserved. This conservative rule is a design choice, not a claim that low risk
proves safety. General/unknown inputs with no supported tactics get no matching
scam-pattern claim, even when their risk is high.

For medium/high risk, family/bank/invoice routes take priority. Otherwise link
evidence selects the internal link route; suspicious-payment uses payment checks;
the remainder uses general verification. Gift-card and link actions are appended
only when supported. Invoice wording mentions *changed* details only when a
changed-details signal supports that observation.

The explicit alias table lives in `context.py`; for example `urgent_request`,
`urgency`, `urgency_pressure`, and `immediate_action_required` map to urgency.
Case, spaces, and hyphens are normalized internally only. Unknown types are not
guessed from free-form prose. Evidence containing an explicit HTTP(S)/www address
or a click/open/follow-link instruction supports link-safe guidance. Payment-type
evidence can additionally support gift-card or changed-payment concepts.
`matched_signals` keeps the original supplied types, deduplicated in input order,
and includes only signals used in social wording. Scenario-only or payment-field
matches may therefore have an empty `matched_signals` list.

## Legacy compatibility and integration concern

`build_intervention()` returns exactly:

```text
{"question": string, "context": string, "recommended_actions": [string]}
```

`question` maps to questioning.message, `context` to diversion.message, and
`recommended_actions` to diversion action labels. Only this adapter accepts the
old UI risk aliases `moderate` → `medium`, `unknown` → `uncertain`.

The current `ui.integration.build_intervention(..., demo=False)` already loads
`intervention.build_intervention`, so the default live Pause & Verify page can
use this adapter without editing frontend files. Its configurable module override
still takes precedence. Demo mode continues using the existing fictional fixtures.

**The current `ui.integration.normalize_analysis()` drops `scenario`.** The adapter
does not reconstruct it from sender names or prose. That path remains functional
with general/signal-based guidance but cannot provide full scenario specificity.
Denise should retain the raw analyzer result and pass it directly to
`build_interventions()`, then store the returned cards alongside the UI-normalized
analysis. Mapping a normalized result's risk back does not recover its scenario.
No frontend files or analyzer contracts were modified in this implementation.

## Personalized verification questionnaire

An additive, interactive layer on top of the same analysis. Two public functions,
both deterministic, synchronous, local, offline, and non-mutating. They add no AI
calls and do not change `build_interventions()` or any strategy schema.

```python
from intervention import build_questionnaire, review_questionnaire

questionnaire = build_questionnaire(analysis)        # 3-5 contextual questions
feedback = review_questionnaire(questionnaire, answers)  # structured review
```

Pass the original seven-field `analyzer.analyze_input(confirmed_text)` result, exactly
as for `build_interventions()`. Do not pass the UI-normalized analysis, which drops
`scenario`.

### `build_questionnaire(analysis)`

Selects 3-5 fixed verification questions personalized by scenario, warning signals,
and the presence of grounded details. Question wording is fixed and never embeds
submitted text; personalization is expressed only as *which* questions appear.

Output (UI-agnostic, JSON-serializable):

```text
{
  "questions": [
    {"id": string, "text": string, "explanation": string}
  ]
}
```

- `id` — stable identifier from a controlled registry; unique within a questionnaire.
- `text` — the question to display.
- `explanation` — one sentence on why it matters (always present).

Answer-interpretation metadata is intentionally **not** in the output; it lives in an
internal registry keyed on `id`, so a forged or malformed questionnaire cannot dictate
conclusions. Unknown IDs are ignored.

### `review_questionnaire(questionnaire, answers)`

`answers` is a dict keyed by question `id`, each value one of `"yes"`, `"no"`,
`"unsure"` (case-insensitive, trimmed). Returns:

```text
{
  "headline": string,
  "summary": string,
  "concerns": [string],
  "recommended_actions": [string]
}
```

Interpretation is **question-aware**, not a yes/no count and not a second fraud score:

- Verification questions ("Have you checked ...?"): **no** is a verification gap,
  **yes** is a reported step (never treated as proof), **unsure** is unresolved.
- Warning questions ("Are you being pressured ...?"): **yes** is a warning sign,
  **no** is reassuring, **unsure** is unresolved.

So the same `"yes"` is reassuring for one question and concerning for another.

**Incomplete / malformed answers.** Partial answers are supported. A missing or
invalid answer (unknown value, wrong type) is treated as *unresolved*, never as fraud.
`answers` that is not a dict is treated as empty. Answer keys not in the registry are
ignored. If no in-scope questions can be identified, a neutral, safe review is returned
whose only recommended action is the standing "do not send money ..." step.

The review never concludes that a request is "safe", "legitimate", "verified", or
"confirmed fraud" from answers alone; `recommended_actions` always ends with an
independent-verification reminder, and `concerns` is never empty (an all-clear set
still returns a caution that the answers do not prove the request is genuine).

### Grounded government/agency subtype

The analyzer has no IRS/government scenario enum, and none is added. When a message is
concerning (medium/high risk) and a government/agency indicator (e.g. IRS, Social
Security, immigration, "arrest"/"warrant", "back taxes") appears in the structured
`claimed_sender` field or in signal evidence — never the free-form explanation — and the
route is not clearly family or invoice, government-tailored questions are selected
(independently checking official notices/records, confirming instructions via an
independently found official website, and threats of penalties/arrest). It never
recommends "Call the IRS" or assumes a particular agency channel, and a plain bank or
generic message is not treated as government impersonation.

### Example — family emergency

Questionnaire (abridged):

```json
{
  "questions": [
    {"id": "contact_relative_known_number", "text": "Have you reached the family member directly using a phone number you already had saved for them?", "explanation": "Reaching the relative on a known number helps confirm who is really asking."},
    {"id": "secrecy_pressure", "text": "Are you being asked to keep this request secret?", "explanation": "Requests for secrecy can prevent independent checks."},
    {"id": "unusual_payment_method", "text": "Are you being asked to pay in an unusual way, such as gift cards, a wire transfer, or cryptocurrency?", "explanation": "Hard-to-reverse payment methods are common in scams."}
  ]
}
```

Review for `{"contact_relative_known_number": "no", "secrecy_pressure": "yes", "unusual_payment_method": "yes"}`:

```json
{
  "headline": "Important verification steps remain",
  "summary": "You reported that you have not reached the relative on a previously saved number, the message pressures you to keep the request secret, and you are being asked to pay in an unusual, hard-to-reverse way.",
  "concerns": [
    "You have not yet reached the relative using a number you already had saved.",
    "Secrecy pressure is a reason to pause before acting.",
    "An unusual, hard-to-reverse payment method is a common scam indicator."
  ],
  "recommended_actions": [
    "Call the family member using a phone number you already had saved, not a number in this message.",
    "Do not keep the request secret; talk it over with someone you trust before acting.",
    "Be cautious with gift cards, wire transfers, or cryptocurrency; these payments are hard to reverse. Verify the request first.",
    "Do not send money or share sensitive details until the request is independently verified."
  ]
}
```

## Sources and research integrity

The following pages were checked on **October 10, 2026**. Runtime uses local
curated records, never fetches these pages. Links are advisory references, not
endorsements or evidence that an agency examined a submitted message.

| Source key | Specific official page | Supported guidance/pattern |
| --- | --- | --- |
| `family` | [FTC: Scammers Use Fake Emergencies To Steal Your Money](https://consumer.ftc.gov/articles/scammers-use-fake-emergencies-steal-your-money) | Check relatives using known numbers and another trusted family contact; emergency impersonation, secrecy, pressure |
| `phishing` | [FTC: How To Recognize and Avoid Phishing Scams](https://consumer.ftc.gov/articles/how-recognize-avoid-phishing-scams) | Check the organization independently; messages posing as banks, links, credential requests |
| `invoice` | [FBI: Business Email Compromise](https://www.fbi.gov/how-we-can-help-you/common-frauds-and-scams/business-email-compromise) | Verify payment instructions and account changes directly; supplier/invoice impersonation |
| `gift_cards` | [FTC: Avoiding and Reporting Gift Card Scams](https://consumer.ftc.gov/articles/avoiding-and-reporting-gift-card-scams) | Gift-card payment demands and requests for card numbers/PINs |
| `general` | [FTC: How To Avoid a Scam](https://consumer.ftc.gov/articles/how-avoid-scam) | Independent contact, time to consider, pressure and impersonation patterns |

Social pattern-to-source keys are inspectable in `social_influence.PATTERNS`;
family/bank/invoice scenario patterns use the corresponding source rows above.
Wording is cautious and never asserts that the submitted sender committed fraud.
The engine does not revalidate quote substrings because it does not receive the
original message: the analyzer remains responsible for that. Accepted evidence
is retained unchanged internally and never turned into user-facing quoted facts.
Free-form explanation is not used to select tactics or construct advice.

Research motivation: [Wang et al., The effect of signal icon and persuasion strategy
on warning design in online fraud, Computers & Security (2022)](https://www.sciencedirect.com/science/article/pii/S0167404822002334).
This implementation is research-informed. Its wording, scenario routing, and
four-card combinations are engineering design assumptions, not experimentally
validated improvements in fraud prevention. No automatic A/B assignment, telemetry,
adaptive optimization, or claims of measured effectiveness are implemented.

## Modules and extension points

| Module | Responsibility |
| --- | --- |
| `intervention.py` | Public bundle/single-strategy APIs, questionnaire APIs, output checks, legacy adapter |
| `interventions/questionnaire.py` | Personalized verification questions and question-aware answer review (additive) |
| `interventions/__init__.py` | Marks the independent backend package |
| `interventions/context.py` | Bounded normalization, frozen context/signals, aliases, internal route selection |
| `interventions/templates.py` | Immutable question/action plans by verification route |
| `interventions/sources.py` | Curated official source metadata and advice |
| `interventions/questioning.py` | Verification questions and stable response options |
| `interventions/authority.py` | Source-backed general advice |
| `interventions/social_influence.py` | Grounded pattern descriptions and original matched signal labels |
| `interventions/diversion.py` | Relevant, independent verification actions |
| `interventions/registry.py` | Explicit allowlist of four callable strategies |
| `interventions/contract.py` | Exact output shape, enum, source, and length validation |

Each strategy exposes `build(analysis: dict) -> dict` and may be imported directly.
`build_strategy()` raises a fixed `ValueError` for unknown names, including module
paths; it never dynamically imports user input. To experiment with alternate
wording, replace a known factory in source code and keep that card's contract.
To add a genuinely fifth strategy, add a module and registry entry, agree a new
version of the bundle contract with the frontend, then update the validator and
tests. Do not silently add a fifth key to the current four-card contract.

To add a scenario template: add an immutable plan, explicitly select its internal
route in context.py, add verified sources and grounded social rules as needed,
and cover the route with tests. Keep public enums aligned with the analyzer; do
not add analyzer enums just to support an internal verification route.

## Running and limitations

```powershell
Set-Location "C:\Visual Studio Folder\ScamBrake"
.\.venv\Scripts\python.exe examples\intervention_examples.py
.\.venv\Scripts\python.exe -m pytest tests/test_interventions.py -q
.\.venv\Scripts\python.exe -m pytest -q
```

The example command prints only fictional fixtures and their generated JSON; the
production engine never prints user content. Backend examples also run with
`python -S` (site packages disabled). Tests use the repository's existing pytest.

Limitations: US-centric advice, manually maintained source URLs, imperfect upstream
scenario/signal labels, bounded aliases, no independent identity or factual
verification, and no measured behavioral effectiveness. An adversarial or mistaken
but structurally valid upstream classification can select an inappropriate card.
Conservative fallbacks can omit useful specificity. User confirmation of a
question or checklist is not proof of safe payment. Denise's four-card UI remains
a separate integration task; no UI redesign is included.
